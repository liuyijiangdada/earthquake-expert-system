# 第5章 向量检索与上下文增强

**说明：** 与 `rag/emergency_rag.py`、`app.py` 中 `_build_rag_section` 及 `config.config` 中 RAG 相关项一致。可经 `scripts/export_md_to_docx.py` 导出 Word。

---

## 5.1 应急知识分块与向量化

### 5.1.1 语料组织与分块粒度

应急知识来源于 `data/emergency_knowledge.json`（路径由 `EMERGENCY_KNOWLEDGE_FILE` 指定，支持相对项目根目录解析）。向量检索侧采用 **topic 级分块**：对每个 `topics` 数组元素构造一条检索单元，**不**将 `topic_relations` 与文件级 `meta` 纳入 RAG 语料，以保证每条 chunk 对应一个可独立阅读的应急主题。

单条 chunk 的正文由以下部分顺序拼接而成：

1. **标题** `title` 与 **类别** `category`（换行分隔）；  
2. 该主题下全部 **步骤** `steps`：先按 `order` 字段排序（非法或非数值时按 0 处理），再将各步 `text` 按行连接。

由此得到的 `text` 字段既保留「主题—有序步骤」结构，又适合作为整段输入编码器。同时保留 `topic_id`、`title`、`source` 等元数据，供检索结果展示与调试（如 `API_DEBUG_RAG` 返回 `rag_topic_ids`）。

该粒度与第 4 章图谱中 `EmergencyTopic`—`HAS_STEP`—`GuidanceStep` 同源数据对应：图谱侧重关系与约束查询，RAG 侧重**同一 JSON 的扁平文本语义匹配**，二者在提示中并列出现时可相互补充。

### 5.1.2 嵌入模型选择与离线加载

系统使用 **SentenceTransformer** 将查询句与各 chunk 的 `text` 编码为稠密向量。默认模型名为 `BAAI/bge-small-zh-v1.5`（`RAG_EMBEDDING_MODEL`），适合中文语义检索场景。初始化时根据 `RAG_EMBEDDING_LOCAL_FILES_ONLY` 决定是否仅使用本地缓存权重，与项目整体**离线部署**策略一致：需事先将模型下载至本机缓存，避免服务启动时访问外网。

编码时对每条文本调用 `model.encode(..., normalize_embeddings=True)`，使向量便于用内积或归一化后的余弦形式计算相似度。启动阶段对**所有 chunk 预计算向量**并堆叠为矩阵 `N×d`（`N` 为主题数，`d` 为嵌入维度），查询时仅对当前用户问句编码一次，降低在线延迟。

若 JSON 不存在、无有效 topic、或嵌入模型加载失败，`build_emergency_rag_from_config` 返回 `None`，应用层将 RAG 段置为占位文本，不阻断大模型路径（见 5.3.2）。

## 5.2 Top-K 检索与排序策略

### 5.2.1 相似度计算与 K 值设定依据

记查询向量为 $\mathbf{q}$，第 $i$ 条 chunk 向量为 $\mathbf{m}_i$（行向量堆叠成矩阵 $\mathbf{M}$）。实现中对 $\mathbf{q}$ 与 $\mathbf{M}$ 各行做 L2 范数归一化（数值上配合 `1e-12` 防止除零），相似度采用**余弦形式**，等价于归一化后的内积：

$$\mathrm{score}_i = \frac{\mathbf{m}_i^\top \mathbf{q}}{\lVert \mathbf{m}_i\rVert\,\lVert \mathbf{q}\rVert}$$

对所有 $\mathrm{score}_i$ 降序排序，取前 **K** 条。K 由配置 `RAG_TOP_K` 控制（默认 5），且实现中取 `min(K, N)`，防止主题总数不足 K 时越界。

K 的取值需在**召回覆盖面**与**提示长度、噪声**之间折中：K 过小可能漏掉相关主题；过大则易引入弱相关段落，挤占图谱与规则文字空间。可结合第 7 章实验在不同 K 下观察回答质量，或与 `LLM_INPUT_MAX_TOKENS` 联合考量。

### 5.2.2 长度截断与展示策略

检索返回的每条命中包含完整 `text` 及 `score` 等字段；写入大模型提示前，应用层对正文做**字符级截断**：仅取 `text` 的前 `RAG_MAX_CHUNK_CHARS` 个字符（默认 800）作为展示体，再与序号、`topic_id`、`title` 格式化为多行字符串。

该截断目的为：（1）控制单次问答中【参考资料】总长度，降低超出最大输入 token 的风险；（2）保留标题与 topic 标识，便于模型区分条目来源。超长步骤列表可能在截断处被切断，此时图谱分支若已命中同一主题的步骤结构，可部分弥补完整性（第 4 章）。

## 5.3 参考资料与提示拼装

### 5.3.1 检索片段格式化

函数 `_build_rag_section` 根据配置 `RAG_ENABLED` 与全局 `emergency_rag` 是否可用，分三种情况返回字符串与命中列表：

- **RAG 关闭**：正文为「（本路径已关闭）」，命中为空列表，用于消融实验。  
- **索引未构建**：正文为「（无相关条目）」，命中为空。  
- **正常检索**：对 Top-K 结果逐条格式化为：

  `序号. [topic_id] 标题` 换行后接截断后的正文。

多条之间以换行拼接，形成单一字符串作为【参考资料】块内容。可选调试模式下将 `rag_topic_ids` 等元数据随 API 返回，便于核对检索是否与预期主题一致。

### 5.3.2 与图谱段落在提示中的位置关系

在 `generate_response` 中，用户提示采用固定顺序：**先【知识图谱】、再【参考资料】**，其后为事实优先级与回答要求等规则文字，**最后为【问题】及用户原始问句**。该顺序与第 3 章协同设计一致：结构化事实与检索片段先于冗长规则，**问题固定置于末尾**，以便在 tokenizer 采用左侧截断时优先保留问句与对话模板中的生成起始标记。

规则中明确：**可验证事实以知识图谱为准，参考资料作步骤与表述补充**；二者均未有效命中时，允许模型基于参数知识回答并说明未命中本地库。RAG 段不参与 `query_type: kg` 的列表查询，仅服务于大模型生成路径。

## 本章小结

本章描述了应急知识 **topic 级分块** 的构造方式、**SentenceTransformer** 嵌入与**离线加载**策略，以及 **余弦 Top-K** 检索与 **RAG_TOP_K**、**RAG_MAX_CHUNK_CHARS** 的作用。进一步说明了参考资料的**列表化格式**及其在提示中相对**知识图谱段与【问题】**的位置关系。第 6 章将图谱、RAG 与 LoRA 大模型在 Flask 中的完整推理与部署串联说明。
