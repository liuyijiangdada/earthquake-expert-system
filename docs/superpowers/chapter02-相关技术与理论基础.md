## 2.1 架构图

本章所述系统采用浏览器 / 应用服务 / 数据与模型分层结构，并通过 REST 接口完成问答、图谱查询与数据更新。以下结合图示说明总体架构、典型数据流及模块与技术栈的对应关系（图文件见 `fig-2-1-1`～`fig-2-1-3`）。

### 2.1.1 系统总体逻辑架构

系统自上而下可分为**展示层**、**应用服务层**与**数据及模型层**，配置信息集中由 `config/config.py` 管理。

**展示层**为静态页面 `static/index.html`，负责用户对话、地震事件列表与条件筛选，以及触发服务端数据刷新。用户与服务器之间通过 HTTP 传输 JSON 格式的请求与响应。

**应用服务层**基于 Flask 在 `app.py` 中实现。对外提供三类主要能力：（1）`POST /api/query`，根据 `query_type` 区分大模型问答（`llm`）与纯图谱查询（`kg`）；（2）`POST /api/update-data`，驱动知识图谱与外部地震目录的增量更新；（3）`GET /` 返回主页面。大模型问答路径中，由 `generate_response` 汇总知识图谱上下文、向量检索得到的参考资料，并调用本地加载的生成模型。

**数据与模型层**包括三部分。**Neo4j 知识图谱**存储地震事件、区域、应急主题及处置步骤等实体与关系，由 `kg/neo4j_kg.py` 封装访问逻辑。**RAG 向量检索**在内存中维护应急知识文本分块的句向量矩阵，检索逻辑见 `rag/emergency_rag.py`，嵌入模型可在配置中指定（如 `BAAI/bge-small-zh-v1.5`）。**本地大模型**采用 Hugging Face `transformers` 加载因果语言模型基座，并通过 `peft` 挂载 LoRA 适配器权重，在 CPU / CUDA / Apple MPS 等设备上推理。

配置模块以虚线方式关联各层，用于统一管理 Neo4j 连接、数据路径、RAG 开关与 Top-K、大模型解码参数及离线加载策略等，保证部署与实验消融（关闭图谱上下文或关闭 RAG）可通过配置完成。

### 2.1.2 数据流与请求处理流程

**（1）大模型问答流（`query_type: llm`）**  
用户输入自然语言问题后，前端将文本置于 `params.input` 发送至 `/api/query`。服务端进入 `generate_response`：在开启图谱上下文时，依据问句中的省区名称、震级比较模式及应急相关触发逻辑，向 Neo4j 发起子图或列表查询，将结果格式化为「知识图谱」文本块；在 RAG 启用且索引已构建时，对用户问题与知识块向量做相似度计算，取 Top-K 片段作为「参考资料」。随后将上述两块内容与规则说明、用户问题按固定模板拼接为单条 user 消息，并与 system 角色说明一起套入与微调一致的聊天模板（如 `<|system|>…</s><|user|>…</s><|assistant|>`）。经分词器编码、在最大长度限制下**左侧截断**以保留末尾问题与生成起始标记后，由 `model.generate` 自回归解码，将新增 token 解码为字符串，封装进 JSON 的 `response` 字段返回。该流程强调**图谱事实与检索片段先于规则与问题**，且**问题位于提示尾部**，与长上下文截断策略一致。

**（2）图谱直连查询流（`query_type: kg`）**  
前端列表与筛选无需经过大模型。请求中通过 `params.type` 指定 `all`、`by_region`、`by_magnitude` 或 `by_depth` 等，服务端直接调用 `Neo4jKG` 相应查询方法并返回结构化结果列表。该路径延迟低、结果可严格复现，适合震级区间、深度区间与地区过滤等交互。

**（3）数据更新流**  
用户触发更新时，调用 `POST /api/update-data`，服务端执行 `kg.update_from_realtime_data()`，在实现中可对接外部地震目录接口（如 USGS GeoJSON），将新事件写入或合并进 Neo4j，并返回更新条数等信息。

### 2.1.3 技术栈与模块映射关系

各功能模块与实现载体之间的对应关系可归纳为：**前端**（`static/index.html`）负责呈现与发起请求；**应用网关**（`app.py`）负责路由与编排；**知识图谱**（`kg/neo4j_kg.py` + Neo4j）负责结构化存储与 Cypher 查询；**向量检索**（`rag/emergency_rag.py`）负责应急 JSON 的分块、嵌入与相似度检索；**大模型**（`transformers` + `peft`）负责条件生成；**配置**（`config/config.py`）贯穿上述组件。详细对照见同目录表格式示意图（`fig-2-1-3-tech-stack.svg`）。离线部署时，基础模型与嵌入模型需预先缓存至本机，并在应用启动阶段设置仅本地加载，避免运行时依赖外网拉取。

## 2.2 知识图谱与图数据库

### 2.2.1 知识图谱基本概念与建模思想

知识图谱以**有向图**形式组织信息：节点表示实体（如地震事件、行政区域、应急主题），边表示实体之间的关系（如发生于、包含步骤、关联主题等）。与纯文本库相比，图谱便于表达**多元关系**与**可组合查询**（例如按地区、震级范围过滤事件），并支持对查询路径的解释，有利于应急等强事实场景下的核对与追溯。

建模上通常区分**模式层**与**数据层**：模式层定义节点标签、属性键及允许的关系类型，有时辅以唯一性约束保障主键语义；数据层则导入具体实例。地震应急场景中，常见设计是将**目录型事实**（时间、地点、震级、深度等）与**规程型知识**（主题—分步指引）纳入同一图或通过关系关联，使一次问答既能引用事件记录又能引用处置要点。后续章节将结合 Neo4j 中的标签与约束具体展开。

### 2.2.2 图数据库与 Cypher 查询概述

**图数据库**将图结构持久化，并提供面向模式的查询语言与索引能力。**Neo4j** 是广泛使用的原生图数据库之一，其查询语言 **Cypher** 采用「模式—匹配」语法，例如用 `(n:Label)` 表示带标签的节点，用 `-[:REL]->` 表示有向关系，用 `WHERE` 子句添加属性过滤与字符串匹配条件。

典型操作包括：（1）**按属性或地理位置相关字段过滤**地震节点；（2）**沿关系遍历**应急主题与步骤子图；（3）利用**唯一性约束**避免重复导入同一事件或同一主题。应用层将 Cypher 封装在 Python 访问类中，根据 HTTP 参数或自然语言规则构造查询，再将结果集序列化为自然语言片段供大模型使用。与关系型数据库相比，多跳关联与半结构化扩展在图模型中往往更直观，但需权衡模式设计与维护成本。

## 2.3 文本向量表示与相似度检索

### 2.3.1 句向量模型与语义检索

**句向量（sentence embedding）**将整段文本映射为固定维度的实数向量，使语义相近的句子在向量空间中彼此靠近。实现上常采用基于 **Transformer** 的编码器，在通用语料或双语料上预训练后，通过句对分类、对比学习或均值池化等方式得到句级表示。中文应急领域场景中，可选用中文语义检索常用的嵌入模型（如 **BGE** 系列），在离线环境下将模型权重缓存至本地，对知识库中的每个文本块编码一次并缓存向量矩阵。

**语义检索**与字面匹配（如关键词倒排索引）互补：用户问题表述多样时，稠密向量检索仍能召回语义相关的段落，适合条例说明、科普解释类内容。系统实现中将应急知识 JSON 按主题或段落组织为若干 **chunk**，逐条编码后与查询句向量进行相似度比较，作为 RAG 的检索前端。

### 2.3.2 相似度度量与 Top-K 检索

给定查询向量 $\mathbf{q}$ 与库中向量 $\mathbf{v}_i$，常用 **余弦相似度**

$$\mathrm{sim}(\mathbf{q}, \mathbf{v}_i) = \frac{\mathbf{q}^\top \mathbf{v}_i}{\lVert \mathbf{q}\rVert\,\lVert \mathbf{v}_i\rVert}$$

衡量方向一致性，取值通常在 $[-1,1]$（具体取决于模型输出是否已归一化）。检索阶段按相似度降序排序，取前 **K** 条作为上下文候选；K 过大易引入噪声并挤占提示长度，过小则可能遗漏要点，实践中常结合验证集或人工抽样确定，并与单条片段最大字符数（如 `RAG_MAX_CHUNK_CHARS`）联合控制总长度。

## 2.4 检索增强生成与大语言模型

### 2.4.1 大语言模型与提示学习

**大语言模型（LLM）**通常指在大规模文本上预训练的**自回归**语言模型，即根据前文预测下一 token 分布，迭代生成完整回复。面向对话或任务型应用时，常将系统说明、用户输入与历史轮次组合为单一字符串，经**分词器**转为 token id 序列输入模型；解码阶段可采用贪心、束搜索或带温度、Top-p 的采样策略，以在流畅度与多样性之间折中。

**提示学习（prompting）**强调通过自然语言指令与上下文布局引导模型行为，而无需改动全部参数。在领域系统中，往往固定**角色设定**（如「地震专家」）、**输出格式要求**（分条、勿使用特定符号等）以及**事实优先级规则**（以图谱为准、文献补充等）。若模型经指令微调，还需保证推理时模板与训练时**聊天标记**（如 `<|system|>`、`<|user|>`、`<|assistant|>`）一致，否则分布偏移会导致生成异常。长提示场景下，还需关注**最大输入长度**与**截断方向**：若截断掉末尾的用户问题或 assistant 起始标记，将导致无效或空输出，因此常采用从左侧截断、保留尾部任务相关片段的策略。

### 2.4.2 检索增强生成（RAG）基本范式与适用场景

**检索增强生成**将外部非参数化知识库以检索结果形式注入提示，再交由 LLM 综合生成答案，典型流程为「检索—拼接—生成」[3]。其动因在于：参数记忆容量有限且难以频繁更新，显式引用片段可提高可追溯性并减轻部分事实幻觉。

在垂直领域实现时，需设计**语料切分粒度**、**检索器类型**（稠密、稀疏或混合）、**重排序**与**提示模板**。地震应急场景中，条文式步骤与固定表述较多，稠密向量 Top-K 往往即可覆盖常见问法；对强结构化查询（如「某省近期地震列表」）则更适合由图谱或 SQL 精确返回，再与 RAG 片段一并写入提示。与纯 RAG 相比，**图谱 + 向量**协同可在同一回答中兼顾可验证事实与灵活表述，具体融合方式在第 3 章及以后章节展开。

## 2.5 参数高效微调（LoRA）概述

### 2.5.1 全量微调与高效微调的动因

将通用 LLM 适配到特定领域或指令风格，常见做法是**监督微调（SFT）**，即用领域问答、对话或指令—回答对继续训练模型参数。若对全部权重更新，称为**全量微调**，其对显存、时间与数据量要求较高，在消费级硬件或频繁迭代场景下成本突出。

**参数高效微调（PEFT）**旨在仅训练少量附加参数或低秩修正，使大部分预训练权重保持冻结，从而在有限资源下近似全量微调效果。该类方法便于多任务间切换适配器、降低过拟合风险，并缩短单次实验周期。

### 2.5.2 LoRA 原理与在领域适配中的作用

**LoRA（Low-Rank Adaptation）**假设权重更新矩阵具有较低秩结构，将某线性层的增量表示为两个小矩阵的乘积 $\Delta W = B A$（秩 $r \ll \min(d_\text{in}, d_\text{out})$），训练时仅更新 $A$、$B$，前向传播时在原权重上叠加 $\Delta W$ [6]。推理阶段可将适配器合并回主干或保持挂载，由 `peft` 等库与 Hugging Face 模型集成。

在地震应急问答中，LoRA 可用于对齐**语气、格式与任务约束**（如简洁、分条、优先安全提示），使模型更稳定地遵循系统提示中的规则；但**数值事实与具体事件**仍应主要依赖图谱与检索片段提供，微调本身不能替代外部知识。系统实现中采用指定基座（如 Qwen1.5-1.8B）与本地 LoRA 目录，在应用启动时加载 `PeftModel`，与第 6 章部署细节一致。

## 本章小结

本章从三个方面为后续方法与设计提供基础：一是给出**分层架构**及 **llm / kg / 更新** 三类数据流，并明确与仓库中模块文件的对应关系；二是介绍**知识图谱与 Neo4j/Cypher**、**句向量与余弦 Top-K 检索**的概念与在本系统中的作用；三是概述 **LLM 提示与 RAG 范式**及 **LoRA 参数高效微调**的动机与要点。第 3 章将在上述技术基础上，形式化地震应急问答任务并给出图谱与向量检索协同的总体方法。
